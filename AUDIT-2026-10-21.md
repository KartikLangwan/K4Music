# K4 Music repository audit — 21 October 2026

## Result and scope

The source review identified **18 actionable defects: 4 high-priority data-integrity issues (P1), and 14 medium-priority correctness/reliability issues (P2)**. Fix the data-integrity issues before distributing another release. Separate release-engineering concerns appear below.

This was an audit-first pass. Application code, configuration, installers and existing tests were not edited. This report is the only intended tracked addition; verification commands generated normal ignored build/cache output.

Reviewed areas: Android service/resolver/recovery, cache and downloads, queue controls, local discovery, database and backup/restore; Windows startup/IPC, libmpv controller, queue persistence, radio, downloads, database, updater, installer and collection UI; shared playlist import, Python bridge, Innertube/Piped and other providers; shared Compose utilities, manifests, Gradle/native packaging, CI and release documentation. Shared UI/helper code received targeted inspection rather than a claim that every resource and line was manually proved correct.

Findings below are source-traced defects with explicit triggering conditions. Their occurrence was not reproduced on a phone or against a user's live library. Potential data-loss paths were inspected without executing destructive scenarios.

## P1 — data integrity

### F01. Windows applies a pending restore before acquiring single-instance ownership

**Evidence:** `windows/src/main/kotlin/com/k4music/desktop/Main.kt:62`, `:72`; `windows/src/main/kotlin/com/k4music/desktop/data/Maintenance.kt:49–52`.

**Trigger:** stage a restore in the running app, then launch a second instance or run the updater's `--quit` invocation before closing the first instance. The second process applies the restore before learning that an instance already owns the app. It attempts to delete the active WAL/SHM and overwrites the first process's open main database. File locking can make this fail partway; it does not make the sequence safe.

**Impact:** loss of active database state, inconsistent database/journal files, failed restore or corruption.

**Fix direction:** acquire ownership first; only the owning process may apply a restore, before opening Room. A forwarding/quit-only process must never mutate the database.

### F02. Windows uninstall recursively deletes the entire user-selected installation folder

**Evidence:** `windows/installer/K4Music.iss:90–92`.

**Trigger:** select an existing directory during first installation, or later put unrelated files beneath the installation directory, then uninstall. `[UninstallDelete]` removes `{app}` recursively, including files absent from the install log. The later prompt concerning library data does not protect this directory.

**Impact:** unrelated user files are deleted.

**Fix direction:** rely on the installed-file log, with narrowly enumerated generated tool leftovers. Do not recursively delete the installation root.

### F03. Windows restore overwrites the only active database non-atomically

**Evidence:** `windows/src/main/kotlin/com/k4music/desktop/data/Maintenance.kt:49–54`.

**Trigger:** disk-full, copy I/O failure or process termination during `pending.copyTo(db, overwrite = true)`. The destination can be truncated or only partly copied even though the error says the current library is kept. On the next launch, the retained pending restore retries and first replaces `.before-restore` with the damaged current file.

**Impact:** a failed restore can destroy both the active library and its previously good recovery copy. This remains a defect even after F01 is fixed.

**Fix direction:** completely stage and sync the replacement, validate it, then use an atomic replacement strategy with a preserved rollback. Keep rollback until the new database successfully opens.

### F04. Android and Windows backup copy the live database without a consistent snapshot

**Evidence:** `app/src/main/kotlin/com/k4music/android/ui/screens/settings/DatabaseSettings.kt:60–63`, `:100–109`; `windows/src/main/kotlin/com/k4music/desktop/data/Maintenance.kt:18–20`.

**Trigger:** background playback/history/import/download writes continue while a checkpoint is followed by an ordinary file-stream copy, especially to a slow Android document destination. The checkpoint finishes before copying and provides no lock for the copy's duration. A concurrent subsequent checkpoint can change main-file pages during the copy. Android's pre-restore recovery copy has the same issue.

**Impact:** a backup can report success while containing mixed database states and be unusable when needed.

**Fix direction:** create a SQLite-consistent snapshot using the backup API or supported snapshot/export operation; alternatively coordinate all database writers and connections for the entire copy. A preliminary checkpoint alone is insufficient. This inference follows SQLite's [documented backup corruption scenario](https://www.sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active).

## P2 — playback, library and import correctness

### F05. A Spotify search timeout aborts import and leaves its progress UI stuck

**Evidence:** `app/src/main/kotlin/com/k4music/android/playlistimport/SpotifySource.kt:111–113`; `app/src/main/kotlin/com/k4music/android/playlistimport/PlaylistImportDialog.kt:95–120`.

The internally imposed 15-second `withTimeout` throws `TimeoutCancellationException`. Both the retry helper and match handler rethrow it as cancellation, aborting the whole parallel batch. The dialog also rethrows without replacing `Working`, so a single slow search can leave the progress indicator visible until dismissal. Retrying failed tracks has a comparable cancelled-state problem. The shared matching path is also compiled into Windows.

**Fix direction:** distinguish a locally expired search deadline from external/user cancellation. Retry/report the track failure and always leave a recoverable UI state.

### F06. YouTube search failure prevents the Spotify importer from trying JioSaavn

**Evidence:** `app/src/main/kotlin/com/k4music/android/playlistimport/SpotifySource.kt:207–225`.

`Innertube.searchPage(...).getOrThrow()` occurs before the Saavn call. A YouTube provider exception exits the function, so an available Saavn catalogue cannot resolve the track. This undermines the advertised independent fallback on both platforms.

**Fix direction:** isolate provider failures and attempt Saavn when YouTube fails as well as when it returns no match.

### F07. Completed Saavn downloads lack the metadata required for Android Offline

**Evidence:** `app/src/main/kotlin/com/k4music/android/service/PlayerService.kt:1456–1482`, `:1519–1531`, `:1598–1613`; `app/src/main/kotlin/com/k4music/android/Database.kt:521–585`; `app/src/main/kotlin/com/k4music/android/utils/CacheState.kt:142–145`.

Direct Saavn and smart-fallback branches return before recording `Format`. Offline queries require a non-null content length; cached-completion checks also depend on it. Fully cached Saavn audio can therefore remain absent from Offline and look downloadable again. A fallback using an existing YouTube ID can retain the obsolete source's byte length.

**Fix direction:** record actual source metadata or use authoritative download/cache completion information, including when switching sources.

### F08. Android auto-resume registers duplicate audio-device callbacks

**Evidence:** `app/src/main/kotlin/com/k4music/android/service/PlayerService.kt:374`, `:416–417`, `:879–909`, `:477–500`.

With device auto-resume enabled, startup registers a callback directly and again through the initial preference StateFlow emission. Each registration replaces the stored reference without unregistering the old callback. Disabling unregisters only the newest; the orphan can still call `player.play()` on headphone connection. Destruction also lacks callback cleanup.

**Fix direction:** make registration idempotent and unregister the owned callback on disable and service destruction.

### F09. SponsorBlock hot-loops after the final skip segment

**Evidence:** `app/src/main/kotlin/com/k4music/android/service/PlayerService.kt:805–806`, `:820–822`.

After playback passes the final segment, the loop only yields and continues, repeatedly dispatching player-position reads to Main. It persists for the rest of the song and while paused, until track change or cancellation.

**Impact:** avoidable CPU/battery consumption and UI-thread traffic.

**Fix direction:** wait for a meaningful player-position/state change or use bounded polling while retaining support for seeking backwards.

### F10. Android local-library polling uses a version that does not track ordinary additions

**Evidence:** `app/src/main/kotlin/com/k4music/android/ui/screens/home/HomeLocalSongs.kt:158–160`.

The five-second poll rescans only when `MediaStore.getVersion()` changes. That version does not change for ordinary app-side additions, so newly added songs can remain invisible while this flow stays active. Android explicitly distinguishes version from per-volume generation in its [MediaStore guidance](https://developer.android.com/training/data-storage/shared/media#check-for-updates).

**Fix direction:** observe content changes or use supported generation tracking, with a compatible strategy for older Android versions.

### F11. Android local-library rescans retain deleted songs and stale tags

**Evidence:** `app/src/main/kotlin/com/k4music/android/ui/screens/home/HomeLocalSongs.kt:187`; `app/src/main/kotlin/com/k4music/android/Database.kt:732–733`.

The scan only inserts rows and the DAO uses conflict `IGNORE`. Deleted local files leave dead entries in the database-backed library; edited titles/artists never replace existing values, even after restarting the scan. Fixing the rescan trigger in F10 does not fix reconciliation.

**Fix direction:** reconcile the scanned local IDs and update metadata while preserving likes/history/playlist relationships. Define how unavailable local files are represented before removing relational records.

### F12. Windows shutdown does not flush the saved queue

**Evidence:** `windows/src/main/kotlin/com/k4music/desktop/player/QueueStore.kt:22`, `:35–40`; `windows/src/main/kotlin/com/k4music/desktop/player/PlayerController.kt:506–509`; `windows/src/main/kotlin/com/k4music/desktop/Main.kt:133–137`.

Queue changes are saved after 500 ms on a daemon executor. Closing the player merely schedules the final queue/position save and immediately proceeds toward process exit. The last position and recent queue changes may never reach disk; direct `writeText` can also leave a partial file if interrupted.

**Fix direction:** synchronously drain/flush the final save during shutdown and replace the queue file atomically.

### F13. An old radio response modifies a newly selected Windows queue

**Evidence:** `windows/src/main/kotlin/com/k4music/desktop/player/PlayerController.kt:473–482`.

`onTrackFinished` captures queue state, suspends on the related-song lookup, then updates whichever queue is current. If the user selects another album/song or clears the queue during lookup, the stale completion appends the previous radio and advances the new queue, or rewinds/pauses it.

**Fix direction:** cancel stale work or verify a queue/playback generation before applying the response.

### F14. Windows Piped playlist loading runs before its session is ready

**Evidence:** `windows/src/main/kotlin/com/k4music/desktop/ui/screens/PipedScreens.kt:140–143`; `windows/src/main/kotlin/com/k4music/desktop/ui/Common.kt:83–99`.

The first composition has a null session and launches a loader capturing that null. The effect is keyed only by page key/retry count, so the later database session emission does not restart it. On a cold visit the playlist stays empty; the screen does not render the loader's failure/retry state.

**Fix direction:** wait for session readiness or include session identity/readiness in loading keys, and expose failure/retry.

### F15. Windows yt-dlp maintenance timeouts cannot bound a stuck subprocess

**Evidence:** `windows/src/main/kotlin/com/k4music/desktop/data/Maintenance.kt:67–68`, `:76–77`.

The update path reads stdout to EOF before calling timed `waitFor`. A process that hangs with stdout open never reaches its timeout/kill. Version lookup ignores the timed wait result and then performs another unbounded read.

**Fix direction:** drain output concurrently, bound process lifetime first, and terminate/close resources on timeout and cancellation.

### F16. Android yt-dlp update does not activate the newly installed extractor

**Evidence:** `app/src/main/python/download.py:1`, `:18`, `:36–39`; `app/src/main/kotlin/com/k4music/android/ui/screens/settings/OtherSettings.kt:277–296`.

The Python module imports `yt_dlp` once. Pip can install a new version successfully, but future extraction still uses cached module objects in the running Python interpreter. The UI reports success without making a required process restart explicit.

**Fix direction:** make activation/restart part of the update contract. Reloading only the top-level module is insufficient for its already loaded submodules/classes.

### F17. Pagination safety limits silently turn incomplete imports into success

**Evidence:** `app/src/main/kotlin/com/k4music/android/playlistimport/PlaylistImport.kt:115–131`; `app/src/main/kotlin/com/k4music/android/playlistimport/YouTubeMusicSource.kt:78–88`.

A repeated continuation token or the page cap exits collection and returns the accumulated tracks while a continuation still exists. Remaining tracks can be misreported as hidden/unavailable; without a declared total, the shortfall is silent. The existing repeated-token test accepts this partial return.

**Fix direction:** terminate safely with an explicit pagination/truncation error or partial-result status; distinguish unrequested pages from provider-hidden tracks.

### F18. Playlist matching can accept a different song as a successful import

**Evidence:** `app/src/main/kotlin/com/k4music/android/playlistimport/PlaylistImport.kt:160–172`.

Substring title matching plus any matching artist word is sufficient despite a large duration disagreement. For example, wanted `One` by `Metallica` can accept `One Thing` by `Metallica`. Artist names with no words longer than two characters, such as `U2` or `LP`, are treated as automatically matching any artist.

**Fix direction:** require normalized title equivalence or stronger corroboration for partial titles; do not turn an unrepresentable short artist into an unconditional match.

## Release, security and maintainability observations

These are separately tracked concerns rather than additions to the 18 behavioral defects.

1. **Release signing is fixed to the debug config.** `app/build.gradle.kts:98` assigns `signingConfigs.getByName("debug")` to release. The environment-backed `ci` signing config is used by nightly, not release, despite the release comment implying an override. The existing APK independently confirms debug signing. Provision a stable private release identity and an explicit configuration path; changing keys for existing installs requires a deliberate compatibility plan. This audit does not claim the debug private key is publicly known.
2. **CI does not run the product's checks.** `.forgejo/workflows/check.yml` runs Nix formatting/flake checks; `flake.nix` supplies tooling/formatters without Android or Windows test/build checks. There is no checked-in GitHub Actions workflow. `scripts/verify-release.ps1` is useful local Android verification, but omits the Windows build and native installer tests. Fresh green Kotlin tests would not validate the asynchronous paths in this report.
3. **Reproducibility and supply-chain controls are incomplete.** Chaquopy requirements use open-ended minimum versions (`app/build.gradle.kts:203–204`); the Gradle wrapper lacks `distributionSha256Sum`; QuickJS is downloaded without a pinned digest or checked download status (`app/src/main/cpp/CMakeLists.txt:15–16`). Windows pins yt-dlp/QuickJS tool hashes but only checks mpv DLL existence. These are integrity/reproducibility gaps, not evidence that a dependency is compromised.
4. **Windows executes unsigned update installers.** The updater uses a fixed GitHub repository over HTTPS, checks length, then starts the executable without publisher-signature or independently trusted digest verification (`windows/src/main/kotlin/com/k4music/desktop/Updater.kt`). The README already discloses unsigned Windows installers. Publisher signing and verification would strengthen the update trust chain; no actual update tampering was established.
5. **Potential Android Auto rejection crash.** `core/data/src/main/kotlin/com/k4music/core/data/utils/CallValidator.kt:130–131` uses `first` instead of a non-throwing lookup when a known package presents an unlisted signature. The exception escapes the synchronous browser root check. The browser service is disabled by default and can be enabled in settings, reducing exposure. Add an explicit signature-mismatch rejection case when working on Android Auto.
6. **Other follow-up risks:** Windows staged-restore validation checks integrity/version and a few Song columns rather than the complete Room schema; final listening-history writes can race DB closure; delayed playback recovery and Android yt-dlp work need cancellation/generation review. These need focused reproduction before broad claims or fixes.
7. **Maintainability:** Android's PlayerService combines resolution, recovery, media-session controls, notification behavior and device callbacks. Windows has a separate controller and DAO surface, while resource generation/source copying reuse platform-neutral portions. This makes behavior parity and lifecycle testing more valuable than a large architectural rewrite. No new abstraction/dependency is necessary to fix most listed issues.

## Suggested repair order and acceptance evidence

1. **Protect user data:** F01–F04. Use disposable databases/directories to test second launch with a pending restore, copy failures and rollback preservation, concurrent-writing backup consistency, and uninstall preservation of sentinel user files.
2. **Correct imports and offline state:** F05–F07, F16–F18. Verify local timeout versus real cancellation, YouTube failure with Saavn success, completed Saavn downloads offline, repeated pagination tokens, and negative song-match examples.
3. **Fix lifecycle/performance and local discovery:** F08–F11. Prove one registered device callback, none after disable/destroy; bounded SponsorBlock work after the final segment; additions/deletions/tag changes reflected without losing user metadata.
4. **Make desktop shutdown/loading deterministic:** F12–F15. Verify queue/position persistence on immediate exit, radio completion ignored after switching queues, cold Piped page load, and a subprocess that holds stdout open past the deadline.
5. **Tighten release evidence:** stable signing, pinned inputs, product checks in CI, and separate Android/Windows smoke checks. Device audio routing, background playback, effects, visual layout and installer behavior still require runtime validation before calling the release fully verified.

### Found and fixed during the PC click-through

1. **Add to playlist → New playlist did nothing.** The save ran on the first dialog's coroutine scope, which is cancelled as soon as the name dialog replaces it. Text dialogs now run their action in `DialogHost`'s scope. That dialog also had no title.
2. Name dialogs (New playlist, Rename) did not focus the text field and Enter did nothing. They now focus it, select the old name, and Enter confirms.
3. Esc with a menu or dialog open also navigated back. It now only closes the menu or dialog.
4. Clicking Search in the sidebar did not put the cursor in the search box, so typing went to the window shortcuts (Space paused playback).
5. A song's ⋯ menu opened at the left edge of the row. It now opens at the button.
6. Downloads listed both "Remove download" and "Delete" (same action). The duplicate is gone.
7. Library → Artists and Albums were blank when empty. They now explain how to follow an artist or save an album.
8. Home's "Playlists" tile opened Library on Songs, and every visit reset the tab. The tab is kept now.
9. The sleep timer showed "Off" as selected while a timer ran.
10. The pairing code was shown with doubled dashes (`6H6Q--DP2-N-…`) on **PC and Android**; the stored code is already grouped.
11. Unpair's confirmation was titled "Delete"; Copy code gave no feedback.
12. Scan for music gave no feedback. It now says how many files it found.
13. Backup left a `backup-….db.lck` file next to the user's backup.

Not covered by the click-through: tray icon menu, taskbar thumbnail buttons, Discord presence, a real installer/uninstaller run.

### Second pass (review of the whole uncommitted diff + new sync code, more live checks)

Tests after this pass: Windows 53 (one new), Android 116 (2 skipped), 0 failures.

1. **Sync: the two devices could overwrite each other on every round.** Song details (title, thumbnail) merged "local wins", so a phone and PC that store a different thumbnail size for the same song each found `merged != remote` and wrote the relay every time. Every one of those writes spent the relay's 300-writes-a-day budget, and the "nothing changed" shortcut never fired. Now details already on the relay win, and the unchanged check looks only at likes and playlists. New test `differentSongDetailsOnEachDeviceDoNotMakeThemWriteForever`.
2. **Sync: Unpair during a running round could silently re-pair** (the round saved its result over the unpaired state). Both apps now drop a round's result if the pairing changed meanwhile.
3. **Wrong synced lyrics (both apps).** LrcLib entries can have `"duration": null`. The model declared it non-null, so one such entry failed the whole search, and the app fell back to KuGou, which can return a different song (seen live: an English song under "Mala Fama"). The duration is now optional. Matching also allows ±2 s (YouTube said 2:18 where LrcLib has 137 s); it used to require the exact second. Lyrics already saved for a song stay until "Refresh lyrics".
4. **yt-dlp update vs. playback.** The weekly/manual `yt-dlp -U` could run while a song lookup had the same yt-dlp files open, which Windows refuses halfway through. Lookups and the update now share a lock (the update waits for running lookups; a lookup waits for the update and meanwhile falls back to JioSaavn as when YouTube is slow).
5. **Uninstall left the "Start with Windows" entry** when it had been turned on in the app rather than by the installer option. Uninstall now always removes it.
6. Import playlist: the link field was not focused, so a paste went nowhere.
7. The lyrics editor uses the same text dialog as names: Enter is kept as a new line there (only name dialogs confirm on Enter). Checked live.

Checked live and fine: closing to tray keeps playing and a relaunch brings the window back; Import shows a clear error for a non-playlist link; Esc closes only the dialog.
Seen once, not reproduced: after coming back from the tray the window was in the app's borderless full screen (F11 got it out). A second try came back normally maximized.

## P1 — breaks a feature or loses data

### A01. Phone/PC sync cannot work in production today
`api/sync.js` answers 503 because its Upstash/KV variables are not set on the Vercel project (`_counter.js` `configured()`). Both apps then show "Offline or unavailable: Sync server answered 503".
**Fix:** connect an Upstash Redis / Vercel KV store to `k4musicweb1` (variables `UPSTASH_REDIS_REST_URL`/`_TOKEN` or `KV_REST_API_URL`/`_TOKEN`), redeploy, then pair two devices once.

### A02. Sync stops permanently at roughly 1,700 songs
The relay refuses bodies over 700,000 characters (`k4musicweb/api/sync.js:11,58`). The client sends the whole library, uncompressed: ~310 bytes per distinct liked/playlist song (id, title, artists, duration, thumbnail URL), +33 % for base64. Estimated: 1,500 songs ≈ 616 KB (ok), **2,000 songs ≈ 821 KB (rejected, HTTP 400)**. A few large imported YouTube Music playlists plus a couple of years of likes gets a library there. The engine then fails every round with "Sync server answered 400"; nothing explains it.
**Fix:** gzip the JSON before encrypting (≈2.7× smaller on real thumbnail URLs, much more if thumbnails are dropped and rebuilt from the id); raise the limit or split into chunks; map 400/413 to a clear "library too large" message. `SyncEngine.kt:92`, `HttpSyncRelay`.

### A03. Restoring a backup while paired deletes data on the other device
`sync.json` keeps `playlistIds`, `knownLikes` and tombstones. A restore (Android `DatabaseSettings.kt:89-141`, Windows `Maintenance.applyPendingRestore`) swaps the database and leaves that file alone. At the next round `snapshot()` (`SyncEngine.kt:125`) sees every like/playlist that is missing from the restored library as *deleted just now*, writes tombstones, and the other device removes them. Reused autoincrement playlist ids can also attach new playlists to old uuids.
**Fix:** after a restore, reset the sync bookkeeping (keep the code, clear ids/known likes/tombstones) so the first round only merges, or force unpair/re-pair with a warning.

### A04. Starting the app a second time does nothing (and autostart makes it the normal case)
`SingleInstance.forward(args)` sends `"\n"` when there are no arguments (a Start-menu click). `readMessage` drops blank lines, so the owner gets an empty list, and `Main.kt:81` does `lines.forEach { … showWindow() … }` — which never runs for an empty list. A hidden/tray instance stays hidden. Since 2.14.26 the first run registers "start with Windows" and starts minimized (`Main.kt:122-127`, `startMinimizedOnStartup = true`), so after the next login the only way in is the tray icon.
**Fix:** in the handler, call `showWindow()` once per message even with no arguments; add a test (`IpcSafetyTest`) that an empty message still raises the window.

### A05. A crash during a synced playlist update can wipe that playlist on both devices
Windows `DesktopLibraryStore.updatePlaylist` (`data/LibrarySync.kt:53-57`) runs rename, clear and insert as three separate statements (Android wraps them in `transaction{}`). Killing the app between `clearPlaylist` and the insert leaves an empty playlist whose hash changed, so it gets a fresh timestamp, wins the last-writer-wins merge, and empties the playlist on the phone too.
**Fix:** one `@Transaction open suspend fun replacePlaylist(...)` in `LibraryDao`.

### A06. Local-file songs are synced to the other device
`likes()` and `playlists()` do not filter `local:` ids, so a liked MP3 on the PC is created on the phone as a song (`ensureSong`) that points at `C:\Users\…\Music\x.mp3` and cannot play, and the file path leaks into the other device's library. **Fix:** skip ids starting with `local:` in both stores (and in `songMeta`).

## P3 — smaller defects

- **Sync secrets/UX:** the pairing code is stored in plain text (`sync.json`), shown on screen and copied to the clipboard without the sensitive flag; Android "Unpair" has no confirmation (Windows asks); Windows sync strings are hard-coded English (`SettingsScreen.kt:625-662`).
- **`"data": null`** from the relay would be read as the string `"null"` and fail Base64 (`SyncEngine.kt:54`, use `JsonNull` check).
- **Android SponsorBlock** also queries for `local:`/`saavn:` ids (`PlayerService.kt:799-803`); Windows skips them.
- **`StreamResolver.resolve`** registers `invokeOnCompletion` inside `computeIfAbsent` (`StreamResolver.kt:58-60`); if the async finishes first, `remove` on the same key throws "Recursive update". Practically never, but start the deferred lazily and register after insertion.
- **Retry budget** resets only when the song id changes (`Recovery.kt`), so a manual Retry after an error gets no automatic retries.
- **Discord** `readWithTimeout` closes a pipe whose read is blocked; that thread (a common-pool worker) can stay blocked forever (`DiscordPresence.kt:190-215`).
- **Artist links lost** for names containing `, ` or ` & ` (e.g. "Simon & Garfunkel"): `Track.artists` is split on those strings and the count then differs from `artistIds` (`K4Database.kt:81`).
- **Queue persistence:** the whole queue is rewritten and fsynced every 10 s of playback, and radio keeps appending to the queue without trimming (`PlayerController.kt:125-128, 218-230`, `QueueStore.kt`).
- **Downloads:** `reconcile()` re-stats every download on each window focus; deleting the song that is playing fails on Windows (file open).
- **Settings:** an unreadable `settings.json` is replaced by defaults and then overwritten on the next change, with no copy kept (`Settings.kt:31-34`).
- **Local music scan** re-reads tags of every file each time and writes one transaction per file; songs from a folder removed in Settings are never pruned (`LocalMusic.kt:61-70`, `K4Database.kt:134-147`).
- **Android restore** exits the process with no message; Piped-era strings (`instance`, `click_to_select`, `add_account`, `custom_instance`, `base_api_url`, `learn_more`) are probably unused now — check with lint before deleting.
- **`download.py`** returns `json.dumps(extract_info(...))` without `sanitize_info`; harmless today, fragile on a yt-dlp change.
- **Theme** follows the Windows light/dark setting only at start (`Main.kt:324-331`).
- **Relay abuse:** `PUT /api/sync` accepts any 64-hex room from any IP (300 writes/day/IP × 700 KB, 90-day TTL) — a few clients can fill a free Upstash plan. Add a first-writer write token and a storage cap.

## Enhancements (highest value first)

1. **E01 Keep YouTube working: auto-update yt-dlp** on both platforms — weekly in the background (PC: `yt-dlp -U`, per-user installs are writable; Android: the existing pip upgrade) and immediately after repeated extraction failures — and show a small "YouTube source is failing, using JioSaavn" notice instead of switching silently.
2. **E02 Sync v2:** gzip + no thumbnails; per-song merge for playlists (union) instead of whole-playlist last-writer-wins; use the relay's `Date` header (or a hybrid logical clock) so a skewed clock cannot win; match same-name playlists on the first pairing; QR-code pairing and a Crockford alphabet (no 0/O/1/I mix-ups); background sync on Android through WorkManager.
3. **E03 Windows media session (SMTC):** track info on the volume flyout and lock screen, correct media-key routing, and no global hotkey grab.
4. **E04 Sound:** add a limiter after EQ/bass boost (+12 dB bands can clip); replace `dynaudnorm` (changes dynamics, differs from Android) with a static gain from YouTube's `loudnessDb`/ReplayGain; queue the next song with `loadfile append` for real gapless playback; optional crossfade.
5. **E05 Installer size and trust:** an audio-only libmpv build (the 121 MB video build is most of the 116 MB installer); code-sign the installer (free for open source via SignPath or Azure Trusted Signing) to remove the SmartScreen/Smart App Control friction your own memory notes describe.
6. **E06 One version source:** `appVersion` is repeated in `windows/build.gradle.kts`, `Updater.kt` (fallback `"2.14.26"`), `K4Music.iss`, README and the website; generate them from one property and have CI build, tag and publish a release with checksums.
7. **E07 Local library:** incremental scan by `lastModified`+size, batched transactions, and a `WatchService` for new files.
8. **E08 Accessibility and translation:** icon buttons need content descriptions and keyboard focus order (only five `semantics` uses in `windows/.../ui`); move Windows-only English strings into resources.
9. **E09 Small ones:** sleep timer "end of this song"; live system-theme change; an "also back up my sync/settings" option in library backup; a short notice that the app streams from YouTube and an unofficial JioSaavn endpoint (public repo ⇒ takedown risk).

## Suggested order

1. A01 (deploy config), A04, A05, A06 — small fixes, big effect.
2. A02 + A03 together (they both change `SyncEngine`/state handling) before 2.14.26 ships a sync nobody can use.
3. B01, B02, B06, B07, B09, B10, B12.
4. E01 and E03, then the release pipeline items (B14, B15, E06).
